L'architecture en une page

Un développeur seul, quatre sprints d'une semaine, un budget d'API de 20 € : l'architecture privilégie la simplicité d'exploitation, sans sacrifier la robustesse là où le sujet l'exige (APIs externes, données intimes, coûts). Chaque décision ci-dessous est reprise et justifiée dans le document.

1Monolithe Django modulaire + worker

Une seule base de code (apps accounts, dreams, ai, dashboard) déployée en deux processus. Le traitement long (≈ 30 s) sort de la requête HTTP : l'interface reste fluide et les relances ne bloquent personne.

2Fournisseurs IA interchangeables

Transcription, émotion et image passent par trois interfaces Python (KAN-21). OpenAI est le choix par défaut ; Deepgram ou AssemblyAI prennent le relais par simple configuration, sans toucher au métier.

3Émotion calculée en local

Modèle Hugging Face exécuté dans le worker : coût nul, aucun texte transmis à un tiers. Le classifieur par mots-clés de la maquette reste disponible comme repli si le modèle ne se charge pas.

4Budget piloté par la donnée

Chaque appel externe est journalisé (APICallLog) avec sa durée et son coût. Trois seuils (80 %, 95 %, 100 % des 20 €) déclenchent alerte, mode dégradé puis arrêt des appels payants.

5Données intimes protégées par conception

Audio supprimé dès la transcription, rêves filtrés par utilisateur dans chaque requête, prompt d'image minimisé, logs et traces sans contenu de rêve, secrets hors du code.

6Livraison continue et repli local

GitHub Actions : lint, tests (≥ 70 %), image Docker, déploiement Render. La même image tourne en local avec docker compose up si l'hébergement échoue (risque R9).

Convention. Les valeurs marquées à mesurer ou à valider sont des objectifs ou des hypothèses : elles seront confirmées par benchmark_latency.py, par les tests du Sprint 2 ou par la lecture des pages officielles des fournisseurs. Les prix sont ceux de benchmark.xlsx (novembre 2026).

3Séquence clé · traitement complet d'un rêve

3.1 Machine à états d'un rêve

received→transcribing→analyzing→generating→done ·  toute étape→failed→ « Réessayer » reprend à error_step

La tâche est idempotente : une étape déjà réussie n'est jamais rejouée (si transcript existe, la transcription n'est pas refacturée). Un verrou Redis par dream_id empêche deux workers de traiter le même rêve.

4.2 Interfaces internes des fournisseurs (KAN-21)

class Transcriber(Protocol):
    def transcribe(self, audio: Path, *, language: str = "fr") -> Transcript: ...      # texte, modèle, durée facturée

class EmotionClassifier(Protocol):
    def classify(self, text: str) -> EmotionResult: ...                                 # clé, score, distribution

class ImageGenerator(Protocol):
    def generate(self, prompt: str, *, size: str = "1024x1024") -> GeneratedImage: ...   # octets PNG, modèle, coût

# settings.py : le fournisseur est une donnée de configuration, pas du code
AI_PROVIDERS = {"stt": env("STT_PROVIDER", default="openai"), "image": env("IMAGE_PROVIDER", default="openai")}

Chaque implémentation est enveloppée par un décorateur commun qui applique le délai maximal, les relances, le coupe-circuit et l'écriture d'APICallLog. Les tests remplacent les fournisseurs par des doublures (comme les services simulés de la maquette) : aucun test ne consomme de budget.

Dépôt et validation 2 s · mise en file 1 s · transcription 10 s · émotion locale 1,5 s · image 14 s · enregistrement et détection par le polling 1,5 s. Les deux appels externes représentent 80 % du budget de latence : ce sont eux que mesure benchmark_latency.py. Si la transcription dépasse sa part, l'option est le découpage de l'audio ou le fournisseur de secours ; si l'image dépasse, la qualité « basse » (0,005 $) divise le temps.

5.3 Budget API : 20 € pour toute la production

≈ 1 080 rêves

20 € ÷ 0,0184 € par rêve (transcription + image). Avec 30 % de relances : ≈ 830 rêves, largement au-delà des besoins de test et de démonstration.

Trois seuils

80 % e-mail + alerte Sentry · 95 % images désactivées · 100 % plus aucun appel payant (KAN-23).

Deux barrières

Le compteur applicatif (somme d'APICallLog) et une limite de dépense configurée chez le fournisseur à vérifier, en cas de bug du compteur.

Le coût est estimé avant l'appel (blocage si le seuil serait franchi) et enregistré après, à partir des unités réellement facturées. La grille tarifaire est en configuration (variables d'environnement) et non dans le code.

6.2 Pipeline CI/CD

  • Sur chaque PR : ruff, mypy, pip-audit (dépendances vulnérables), python manage.py check --deploy et makemigrations --check, puis pytest avec un service PostgreSQL ; --cov-fail-under=70 bloque la fusion. Fournisseurs IA toujours simulés : la CI ne coûte rien.
  • Sur main : image Docker multi-étapes (modèle d'émotion téléchargé à la construction, utilisateur non root), publiée sur GHCR avec le SHA du commit ; déploiement Render par deploy hook, migrations en étape de pré-déploiement, puis test de fumée sur /healthz. Retour arrière : redéployer le SHA précédent.

6.3 Monitoring, logs et métriques clés

Logs structurés

JSON sur la sortie standard (python-json-logger), un identifiant de corrélation par requête propagé à la tâche Celery (dream_id). Jamais de texte de rêve, de prompt ou d'audio dans les logs : uniquement identifiants, durées, codes.

Erreurs et traces

Sentry sur le web et le worker (intégrations Django et Celery), 10 % des transactions échantillonnées, before_send qui retire les corps de requêtes. Alerte sur nouvelle erreur et sur régression de latence.

Métriques métier

Calculées depuis la base et affichées dans l'admin : coût cumulé et projection, rêves par jour, p50/p95 de processing_ms, taux d'erreur et de relance par fournisseur, part d'images de secours, taux de correction de l'émotion.

Santé et alertes

/healthz (base, Redis, âge de la plus vieille tâche en file) interrogé par une sonde externe ; alertes : budget 80 %, file bloquée > 5 min, taux d'erreur API > 2 % sur 1 h. Revue des métriques à chaque rétrospective.

6.4 Sécurité de l'architecture

HTTPS obligatoire (HSTS, cookies Secure/HttpOnly/SameSite), mots de passe Argon2, CSRF sur tous les formulaires, CSP stricte, uploads validés par signature et taille puis stockés sous un nom aléatoire hors de la racine web, médias servis seulement à leur propriétaire, secrets en variables d'environnement, compte de service à privilèges minimaux pour la base, dépendances auditées en CI. Ces mesures répondent aux risques R2 et R3 et à l'analyse RGPD du dossier de cadrage.
